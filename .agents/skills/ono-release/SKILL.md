# OnO Release Skill

> 이 파일이 `release` 절차의 정본이다. Codex 는 이 파일을 바로 쓰고, Claude Code 의 `/release` 는 `.claude/skills/release/SKILL.md` 래퍼가 이 파일을 읽어 따른다. 절차를 고칠 때는 이 파일만 고친다.

사용자가 `release <버전> [기준 커밋]`(Claude Code 에서는 `/release`), `출시 전 검증`, `배포 전 검증`, `업데이트 내역 작성`을 요청하면 이 Skill을 따른다.

## 목표

앱스토어/플레이스토어 제출 전 최종 게이트다. 순서대로 실행하고 중간에 실패하면 즉시 멈춘다. 운영 중인 앱이므로 정적 검증, 사용자 영향, 반응형 UI, 인증/동기화/알림 부작용을 함께 본다.

**릴리스 빌드 업로드, 스토어 제출, `main` merge, tag 생성은 사람이 한다.** 이 Skill은 그 직전까지 준비하고 안내만 한다. release 브랜치 push 와 develop 대상 PR 은 `pr` 로 한다.

## 0단계 - 출시 범위와 브랜치

- 출시 버전이 없으면 `pubspec.yaml` 의 현재 `version` 과 최근 `release/*` 브랜치를 보여 주고 묻는다.
- 출시 범위: 기준이 주어지면 `<기준>..HEAD`, 없으면 직전 `origin/release/*` 이후 develop 에 들어온 커밋이다. `git log`, `docs/업데이트 내역`, 현재 변경사항을 보고도 기준이 명확하지 않으면 사용자에게 묻는다.
- 브랜치: `git switch -c release/<버전> --no-track origin/develop` 로 만든다(예: `release/4.1.1`). 이미 있으면 그 브랜치에서 진행한다.
- 관련 `docs` 명세서, PR 문서, `docs/업데이트 내역`을 확인해 기능 의도와 사용자 표현을 맞춘다.

## 1단계 - 정적 분석 (CI 와 같은 기준)

```bash
flutter analyze --no-fatal-infos
```

info 는 기존에 많이 쌓여 있어 판정에서 제외한다. warning 이나 error 가 1개라도 있으면 다음 단계로 넘어가지 않는다.

## 2단계 - 테스트

```bash
flutter test
```

단위, 위젯, 골든 테스트가 `test/` 에 있고 CI 도 PR 마다 돌린다. 실패가 있으면 멈추고 원인을 설명한다. 골든이 깨졌으면 의도한 UI 변경인지 먼저 확인하고, 의도한 변경일 때만 사용자 확인 후 골든을 갱신한다. 실행하지 못했으면 통과했다고 쓰지 않고 남은 리스크로 적는다.

## 3단계 - 위험 검토

0단계 출시 범위 diff 를 기준으로 `check` 수준의 검토를 한다. 서브에이전트를 띄울 수 있는 도구에서는 관점별로 병렬로 돌린다.

- 성능: rebuild, jank, 메모리
- 로직: null safety, async 경합, 상태 전이, 에러 처리
- 부작용: API 중복 호출, 로컬 저장, FCM
- 인증과 화면 접근: 토큰, 세션, 라우팅
- 반응형: 작은 폰, 일반 폰, 태블릿, 가로/세로에서 overflow, 버튼 잘림, 스크롤 불가
- API 계약: 응답 필드와 null 가능성이 불명확한데 방어 코드가 없는 곳

## 4단계 - 종합 판정

아래 중 하나라도 있으면 `배포 불가`다.

- `flutter analyze --no-fatal-infos` 에 error 나 warning 이 있다.
- 테스트 실패가 있다.
- 🔴 항목이 1개 이상이다. 런타임 예외, 인증 우회, 데이터 손실, 결제/학습 기록/동기화/FCM 부작용 가능성이 높은 것이 여기 들어간다.
- 작은 폰이나 태블릿에서 핵심 화면을 사용할 수 없는 UI 깨짐 가능성이 높다.

**🟢 배포 가능이면 4-1 ~ 4-3 을 진행한다.**

### 4-1. 버전 올림 커밋

`pubspec.yaml` 의 `version: <버전>+<빌드 번호>` 를 올린다. 빌드 번호는 직전 출시보다 1 크게 한다(스토어에 올린 번호와 겹치면 안 된다). 이 한 줄만 바꿔 아래 형식으로 커밋한다(예: 커밋 b979ac2).

```text
[Chore] <버전> 출시 버전으로 올린다 - <버전>+<빌드 번호>
```

### 4-2. 업데이트 내역 작성

앱스토어/플레이스토어에 바로 붙여 넣을 수 있게 한국어로 작성해 보고에 포함한다.

- 번호가 있는 기능 목록과 짧은 bullet 로 쓴다. 같은 흐름의 세부 변경은 하나의 항목 아래로 묶는다.
- 사용자에게 보이는 변화 중심으로, 초등, 중등, 고등 학생이 이해하기 쉬운 짧은 문장으로 쓴다.
- "개선했습니다", "추가했어요", "볼 수 있어요"처럼 자연스러운 앱 문구를 쓴다.
- 내부 구현명, 클래스명, API명, PR 번호, 커밋 해시는 쓰지 않는다.
- 검증하지 않은 기능, 개발자만 아는 변경, 아직 배포되지 않은 기능은 넣지 않는다.
- 버그 수정은 사용자가 겪던 문제와 좋아진 점을 짧게 설명한다.
- 마케팅 문구처럼 과장하지 않는다.

```text
1. 처음 사용자를 위한 튜토리얼 추가

  - OnO의 주요 기능을 처음부터 쉽게 둘러볼 수 있어요.
  - 공책, 오답노트, 복습 세트, 학습 달력, 복습 리포트 사용 흐름을 차례대로 안내해 드려요.
  - 마이페이지에서 튜토리얼을 다시 볼 수 있어요.

2. 여러 장 오답노트 복습 필기 지원

  - 이미지가 여러 장인 오답노트도 앱에서 바로 풀 수 있어요.
  - 각 이미지에 따로 필기하고, 모든 풀이 이미지를 한 번에 제출할 수 있어요.
```

### 4-3. 사람이 할 일 안내 (실행하지 않는다)

```bash
# iOS 배포 파일 (Xcode Organizer 에서 업로드)
flutter build ipa --dart-define=ENV=prod --release
open build/ios/archive/*.xcarchive
# Android 배포 파일 (Play Console 에 업로드)
flutter build appbundle --dart-define=ENV=prod --release
```

- `release/<버전>` → `develop` PR 은 `pr` 로 만들 수 있다. `develop` → `main` merge 와 스토어 업로드, 심사 제출은 사람이 한다.
- 심사 통과 후에는 아래 5단계 안내를 그대로 붙인다. 콘솔에서 사람이 하는 일이라 실행하지 않고 안내만 한다.

## 5단계 - 단계적 출시 (심사 통과 후)

한 번 나간 버전은 되돌릴 수 없다. 대신 받는 사람을 일부로 묶어 두고 Sentry 를 보면서 넓힌다. 이미 받은 사람은 어쩔 수 없지만 나머지는 막을 수 있다.

### 스토어 설정

| 스토어 | 켜는 곳 | 동작 |
|---|---|---|
| Google Play | 프로덕션 출시 만들 때 **출시 비율**(Staged rollout) 입력 | 비율을 직접 올린다. 문제가 보이면 **출시 중단**(Halt rollout) 하면 더 안 퍼진다 |
| App Store | 버전 페이지의 **단계적 출시**(Phased Release) 선택 후 출시 | 7일 동안 1, 2, 5, 10, 20, 50, 100% 로 자동으로 퍼진다. **일시 정지**(Pause) 할 수 있다 |

- App Store 단계적 출시는 **자동 업데이트에만** 걸린다. 스토어에서 직접 업데이트를 누르거나 새로 설치하는 사람은 바로 받는다.
- Play 비율은 기본으로 **5% → 20% → 50% → 100%**, 단계마다 하루 이상 둔다. 사용자가 적어서 1% 로는 에러가 거의 안 모이므로 5% 에서 시작한다.

### 매 단계 넘어가기 전에 Sentry 에서 볼 것

필터는 `environment:production release:<이번 릴리즈>` 다. 릴리즈 이름은 플랫폼마다 따로 찍힌다.

- Android: `com.ono.app@<버전>+<빌드>`
- iOS: `com.aisip.OnO@<버전>+<빌드>` (iOS 빌드 번호는 pubspec 과 다를 수 있으니 Sentry 의 Releases 목록에서 확인)

| 볼 것 | 멈추는 기준 (시작값) |
|---|---|
| 이번 릴리즈에서 처음 생긴 이슈 | fatal 이 1건이라도 있으면 멈추고 원인부터 본다 |
| 크래시 없는 세션 비율 (Releases 화면) | 직전 릴리즈보다 1%p 넘게 낮으면 멈춘다 |
| 기존 이슈의 급증 | 직전 릴리즈 같은 기간보다 눈에 띄게 늘었으면 멈춘다 |

- 멈추는 기준 숫자는 처음 정한 값이다. 몇 번 출시해 보고 조정한다.
- 크래시 없는 세션 비율은 sentry_flutter 의 세션 추적(`enableAutoSessionTracking`, 기본 켜짐)으로 모인다. 끄지 않는다.
- 멈췄으면 고친 버전을 다시 심사에 올리고, 그 버전을 같은 방식으로 단계적 출시한다.

### Sentry 알림 (한 번만 설정)

매번 들어가 보지 않아도 되게, 새 릴리즈에서 처음 보는 이슈가 생기면 알림이 오게 둔다. Sentry 화면 문구는 바뀔 수 있어서 위치만 적는다.

1. `ai-sip` 조직, `flutter` 프로젝트의 **Alerts → Create Alert → Issues**
2. 조건: 새 이슈가 생겼을 때
3. 필터: environment 가 `production`, 이벤트가 최신 릴리즈에서 온 것
4. 동작: 메일 또는 연결된 알림 채널
