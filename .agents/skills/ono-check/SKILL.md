# OnO Check Skill

사용자가 `check <커밋 번호>` 또는 변경사항 검토를 요청하면 이 Skill을 따른다. 인자가 없으면 현재 작업 중인 변경사항(`git status`, staged/unstaged diff, untracked 파일)을 대상으로 검토한다.

## 목표

변경된 파일과 영향받는 사용자 흐름을 기준으로 위험한 사항과 에러 가능성을 검증한다. 전체 프로젝트를 넓게 훑는 대신 diff와 영향 범위에 집중한다.

## 절차

1. 기준 커밋이 있으면 해당 커밋부터 현재까지의 diff를 확인한다.
2. 기준 커밋이 없으면 현재 작업 중인 변경사항을 확인한다. staged, unstaged, untracked 파일을 모두 대상에 포함한다.
3. 변경 파일별 사용자 흐름, 상태 관리, API 연동, UI 영향을 추적한다.
4. 1차 검사는 diff 기반으로 수행한다.
5. 2차 검사는 1차 결론을 스스로 반증한다. 상위 조건, 호출 가능성, 실제 도달 경로를 다시 확인한다.
6. 가능한 경우 `dart format`과 `flutter analyze`를 실행한다.
7. UI 변경이 있으면 폰과 태블릿 레이아웃에서 깨질 가능성을 반드시 검토한다.

## 자가 반증

위험 보고 전에 반드시 아래 질문으로 2차 검토한다.

- 내가 놓쳤을 가능성이 큰 사용자 흐름은 무엇인가
- 이 변경이 실제 사용자에게 깨질 수 있는 경로는 무엇인가
- 이 위험 판단이 틀렸다면 어떤 상위 조건, 라우팅, 상태 값, API 응답 때문에 틀릴 수 있는가
- 문제가 있다고 본 코드가 실제로 실행되는 경로에 도달 가능한가
- 문제가 없다고 본 코드가 null, 빈 응답, 느린 네트워크, 화면 이탈 상황에서도 안전한가

반증 결과 도달 불가능한 문제는 낮추거나 제외하고, 새로 발견된 위험은 위험도에 포함한다.

## 검토 관점

- null safety와 런타임 예외
- API 계약, 응답 필드, 에러 응답, 중복 요청
- 상태/async 경합, 잘못된 로딩/빈 상태/에러 상태
- 작은 폰, 일반 폰, 태블릿, 가로/세로 화면의 overflow와 스크롤 가능성
- 앱스토어/플레이스토어 배포 후 롤백이 어려운 리스크
- 기존 데이터, 학습 기록, 결제/인증/동기화 흐름 영향

## 보고 형식

검토 결과는 위험도 순서로 작성한다.

- `🔴` 즉시 수정 필요
- `🟠` 배포 전 수정 권장
- `🟡` 확인 필요
- `🟢` 문제 없음

각 항목은 가능한 한 `파일:라인` 근거를 포함한다. 발견한 문제가 없더라도 남은 리스크와 실행하지 못한 검증을 명확히 적는다.

보고 마지막에는 `자가 반증 결과`를 짧게 포함한다.
