# OnO Plan Skill

> 이 파일이 `plan` 절차의 정본이다. Codex 는 이 파일을 바로 쓰고, Claude Code 의 `/plan` 은 `.claude/skills/plan/SKILL.md` 래퍼가 이 파일을 읽어 따른다. 절차를 고칠 때는 이 파일만 고친다.

사용자가 `plan <기능 설명>`(Claude Code 에서는 `/plan <기능 설명>`) 형태로 요청하면 이 Skill을 따른다. 기능 설명이 없으면 명세서를 쓸 수 없으므로 먼저 설명을 요청한다.

## 목표

기능 구현 전에 다른 에이전트도 바로 참고할 수 있는 구현 개요 및 명세서를 작성한다. 이 단계에서는 앱 코드, 설정 코드, 테스트 코드를 수정하지 않는다.

## 절차

1. 요구사항을 한 문장으로 재정리하고, 해석이 여러 가지면 짧게 확인한다.
2. `docs` 아래 기존 기획/PR/명세 문서를 먼저 확인한다.
3. 현재 코드의 화면 흐름, 상태 관리, 라우팅, API 연동 위치를 읽어서 근거를 확보한다.
4. 백엔드 API 계약, 응답 필드, null 가능성, 에러 형태가 불명확하면 임의로 단정하지 않고 "확인 필요"로 둔다.
5. `docs` 아래에 기능을 알아볼 수 있는 새 폴더를 만든다. 폴더명과 파일명은 기존 문서처럼 한글 중심으로 짧게 짓는다.
6. 새 폴더 안에 아래 구성으로 markdown 명세서를 작성한다.
7. 명세서 작성 후 사용자에게 검토를 요청하고, `feat` 를 시작하기 전에 기다린다.

## 명세서 구성

```markdown
# <기능명> 구현 명세서

## 요구사항
- 기능 목표, 사용자 관점에서 어떤 동작이 필요한가

## 영향 범위
- 화면 흐름
- 변경, 추가되는 파일과 위젯, 각 역할
- 영향받는 사용자 흐름

## API/상태 관리
- 사용할 API 엔드포인트와 응답 필드 (확인 안 된 것은 "확인 필요")
- 상태 관리 방식 (이 앱은 `provider` 패키지만 쓴다. `lib/Provider/` 의 기존 Provider 확장인지 새 Provider 인지)
- null, 빈 상태, 에러 상태 처리

## UI 반응형 고려사항
- 폰, 태블릿, 가로/세로에서 처리할 내용

## 구현 단계 (순서대로)
1. ...

## 배포 리스크
- 릴리즈 후 되돌리기 어려운 변경이 있는가

## 검증 방법
- flutter analyze --no-fatal-infos, 관련 flutter test
- 확인해야 할 화면과 시나리오

## 추천 커밋 단위
- [Feat] ... (#이슈번호)
```

## 금지

- 구현 코드 수정
- 테스트 코드 추가
- 불필요한 구조화나 미래 확장용 설계
- 확인되지 않은 API 필드명 또는 응답 구조 작성

## 완료 보고

작성한 문서 경로, 핵심 결정, 남은 확인사항을 간결하게 보고한다.
