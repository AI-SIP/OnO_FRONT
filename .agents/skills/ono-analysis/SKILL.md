# OnO Analysis Skill

사용자가 `analysis <문제 설명>` 또는 원인 분석을 요청하면 이 Skill을 따른다. 인자가 없으면 현재 작업 중인 변경사항(`git status`, staged/unstaged diff, untracked 파일)을 대상으로 분석한다.

## 목표

문제 원인을 코드 근거로 규명한다. 이 단계는 읽기 전용이며, 코드를 수정하거나 커밋하지 않는다.

## 시작 확인

인자가 없으면 먼저 현재 변경사항을 확인하고, 변경된 파일에서 드러나는 문제 가능성과 영향 흐름을 분석한다. 현재 변경사항이 없고 분석 대상도 없으면 사용자에게 분석할 문제나 경로를 요청한다.

다음 정보가 이미 충분하지 않으면 먼저 짧게 확인한다.

1. 어떤 문제나 현상이 발생하는가
2. 원하는 동작은 무엇인가
3. 관련 파일, 위젯, 화면, API 경로가 있는가

## 조사 관점

문제를 다음 차원으로 나눠 본다.

- 위젯 트리와 상태 흐름: 상태가 어디서 만들어지고 어디서 깨지는가
- API와 데이터 흐름: 요청 시점, 응답 shape, nullable 필드, 에러 처리
- 비동기와 타이밍: async 경합, Future/Stream 처리 순서, mounted 체크
- 플랫폼과 화면 조건: Android/iOS, 폰/태블릿, 가로/세로 차이
- 부작용: API 중복 호출, 로컬 저장소, FCM/알림, 화면 재진입 상태

## 절차

1. 관련 문서가 있으면 `docs` 아래에서 먼저 확인한다.
2. 문제의 진입점이 되는 화면, 위젯, 서비스, provider/controller를 찾는다.
3. 위젯 트리, 상태 변경, API 호출 경로를 `파일:라인` 근거로 추적한다.
4. 가능한 원인을 확신도별로 나눈다.
5. 각 원인을 반증한다. 해당 원인이 맞다면 재현 현상이 설명되는지, 상위 조건에서 막히지 않는지 확인한다.
6. 확인되지 않은 내용은 단정하지 않고 "확인 필요"로 둔다.

## 자가 반증

보고 전에 반드시 아래 질문으로 2차 검토한다.

- 내가 놓쳤을 가능성이 큰 흐름은 무엇인가
- 이 원인이 틀렸다면 어떤 조건 때문인가
- 상위 위젯, 라우팅, 상태 초기화, API 응답 처리에서 이미 막히는 경로는 없는가
- 현재 결론이 실제 사용자 재현 조건과 맞는가

반증 결과 1차 결론이 약하면 원인 확신도를 낮추거나 폐기한다.

## 보고 형식

```markdown
## 요약
한두 줄로 핵심 원인

## 근거
- 파일:라인 - 설명

## 원인 목록
1. [높음] ...
2. [중간] ...
3. [낮음] ...

## 확인이 필요한 부분
- ...

## 자가 반증 결과
- ...

## 다음 조치 제안
- ...
```

## 금지

- 코드 수정
- 테스트 코드 작성
- 커밋
- 확인되지 않은 API 응답 구조 단정
