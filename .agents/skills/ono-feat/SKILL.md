# OnO Feat Skill

사용자가 `feat` 또는 `plan 문서대로 구현`을 요청하면 이 Skill을 따른다. 인자가 없으면 최근 `docs` 명세서와 현재 작업 중인 변경사항을 함께 확인해 기준 문서를 찾는다.

## 시작 조건

1. 기준이 될 구현 명세서를 먼저 확인한다.
2. 인자가 없으면 최근 생성/수정된 `docs` 명세서와 현재 변경사항을 확인해 가장 관련 높은 명세서를 찾는다.
3. 명세서가 하나로 명확하지 않으면 사용자에게 어떤 문서를 기준으로 할지 묻는다.
4. 명세서와 실제 코드가 다르면 실제 코드 기준으로 판단하고, 차이를 사용자에게 설명한다.

## 구현 원칙

- 명세서 범위를 벗어나는 기능을 임의로 추가하지 않는다.
- 주변 Flutter 코드의 상태 관리, 라우팅, API 연동, 네이밍, UI 톤을 따른다.
- 운영 중인 앱 기준으로 런타임 예외, null 처리, 빈 상태, 에러 상태, 중복 요청, 로딩 지연을 함께 본다.
- 폰과 태블릿을 모두 1차 사용자 환경으로 보고 반응형 제약을 확인한다.
- 테스트 코드는 사용자가 요청하지 않으면 새로 만들지 않는다.

## 구현 절차

1. 명세서와 관련 코드 파일을 읽는다.
2. 수정 범위를 좁게 정한다.
3. 구현 전 사용자에게 어떤 파일을 어떤 방향으로 바꿀지 짧게 알린다.
4. 필요한 줄만 수정한다.
5. 내 변경으로 생긴 미사용 import, 변수, 함수만 정리한다.
6. 가능한 범위에서 `dart format`과 `flutter analyze`를 실행한다.
7. 화면 변경이면 작은 폰, 일반 폰, 태블릿, 가로/세로에서 깨질 가능성을 검토한다.

## 자가 반증

완료 보고 전에 반드시 아래 질문으로 2차 검토한다.

- 내가 놓쳤을 가능성이 큰 것은 무엇인가
- 이 변경이 실제 사용자에게 깨질 수 있는 경로는 무엇인가
- 명세서 범위를 벗어난 수정이 섞이지 않았는가
- null, 빈 상태, 에러 상태, 느린 네트워크, 화면 이탈 상황에서도 안전한가
- 작은 폰과 태블릿에서 텍스트 overflow, 버튼 잘림, 스크롤 불가 가능성이 없는가

반증 결과 문제가 보이면 완료 보고 전에 수정하거나, 수정하지 못한 경우 남은 리스크로 명확히 보고한다.

## 완료 보고

다음을 간결하게 정리한다.

- 변경한 내용
- 사용자에게 미치는 영향
- 반응형 처리 여부
- 실행한 검증과 결과
- 자가 반증 결과
- 남은 리스크 또는 확인이 필요한 부분
- 추천 커밋 단위와 커밋 메시지

커밋 메시지 형식:

```text
[Feat] 구현 타이틀 - 구현 상세1 구현 상세2
```
