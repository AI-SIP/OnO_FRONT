$ARGUMENTS

어떤 구현 명세서를 기준으로 작업할지 먼저 확인한다. 명확하지 않으면 사용자에게 물어본다.

**1단계 – 명세서·현재 코드 확인**
- 해당 명세서를 읽는다.
- 명세서에 나온 관련 파일·위젯의 현재 코드를 확인한다.
- 명세서와 실제 코드가 다르면, 실제 코드 기준으로 판단하되 차이를 사용자에게 설명한다.
- API 계약이 불명확하면 임의로 단정하지 않고 확인을 요청한다.

**2단계 – 구현**
- 명세서의 구현 단계를 순서대로 진행한다.
- 요청 범위만 수정한다. 무관한 리팩터링·포맷팅·이름 변경 금지.
- 주변 코드 스타일·네이밍·상태 관리 패턴을 따른다.
- 단일 사용처를 위한 불필요한 추상화 금지.
- null safety, async 처리, 에러/로딩/빈 상태를 챙긴다.

**3단계 – 검증**
구현 후 다음을 수행한다.
```
dart format <바꾼 test 파일>         # test 아래 바꾼 파일만. lib 전체 포맷 금지 (무관한 diff)
flutter analyze --no-fatal-infos     # CI 기준. warning, error 가 0개여야 한다
flutter test <관련 테스트>           # 바꾼 동작과 관련된 테스트가 있으면
```
warning 이나 error 가 있으면 수정 후 재확인. 해결 불가능한 경우 사용자에게 설명한다.
편집할 때마다 `.claude/settings.json` 훅이 바꾼 dart 파일을 같은 기준으로 analyze 하므로, 훅이 알려 준 문제는 바로 고친다.

**4단계 – 보고**
아래 항목을 간결하게 정리한다.
- 변경한 내용 (파일:라인 포함)
- 사용자에게 미치는 영향
- 반응형 처리 여부
- 실행한 검증 결과
- 남은 리스크 또는 확인이 필요한 부분
- 추천 커밋 단위와 메시지

**커밋하지 않는다.** 커밋은 사용자가 `/commit` 을 호출할 때 한다.
